The feature: during fast-forward, melonDS keeps Nintendo DS background music at 1x by rendering it on the host while sound effects keep running on the emulated clock. Read docs/design-notes.md first (sections 2, 3, 5.1, 6 and 12 explain the design and known failure modes), then the core code under melonDS/src/Sound/ (SndCmdTracker.{h,cpp} is the state machine, BgmRenderer.{h,cpp} the host renderer, SdatIndex the classifier, TimeStretch the SFX stretcher) and the hooks in melonDS/src/NDS.cpp, melonDS/src/SPU.cpp (Mix and SPUChannel::Start) and melonDS/src/frontend/qt_sdl/EmuInstanceAudio.cpp. The same core is vendored at android/melonDS-android/melonDS-android-lib/src (differs only by VarBool->Bool32); the Android hooks are in android/melonDS-android/app/src/main/cpp/MelonInstance.cpp and OboeCallback.cpp.

How it works: the game's ARM9 sends SNDCommand lists to the ARM7 sound driver over the IPC FIFO (PXI tag 7). The tracker sniffs them in NDS::ARM9IOWrite32 and follows one "host" driver player at a time. The ARM7 keeps playing that sequence (so game-visible state stays faithful) and the SPU mutes its channels: per-frame from the READ_DRIVER_INFO snapshot (ChanOwner) plus per-note at key-on from the driver's live SNDWork in ARM7 memory (SndCmdTracker::ChannelKeyOnMuted, SPUChannel::HostMutedPlayer). The host renderer is paced by the audio device and mirrors fades (PLAYER_PARAM extFader as a 1x-rate glide), pauses, tempo, track params, stops, and crossfades between tracks.

Focus on HANDOFF bugs, i.e. anything that makes the music double, go silent, jump, or stay on the wrong clock around transitions. Walk these scenarios through the code step by step as the command stream a Nitro SDK game (Pokemon Gen 4/5) actually produces, and for each state the exact sequence of tracker/renderer/SPU state changes and where it can go wrong:

1. Fast-forward toggled on mid-song and off again (host stays the source until the next START/STOP by design; check the mute state of hardware notes already sounding at each transition, and PickHost's conditions incl. the SNDSharedWork playerStatus bit).
2. Field BGM paused by PAUSE_SEQ for a battle, battle theme on another player, low-HP theme (BATTLEPINCH) on a third player while the battle theme is paused, then back; then victory jingle (classified BGM because it loops) stealing the host; then the field theme resumed with PAUSE_SEQ(0) and re-adopted mid-song from the tick counter. Check: NoHost[] lifetime, Paused handling in EnterHostMode, tick seek vs the hardware position, fader state carried across host changes, the outgoing voice vs a player that is still audible on hardware, and HostMutedPlayer tags that outlive their host or are evaluated with a stale HostP.
3. A sequence stopped without STOP_SEQ: INVALIDATE_SEQ/INVALIDATE_BANK, heap reuse where a new START lands at the same RAM address as the old sequence, and PREPARE_SEQ without START_PREPARED_SEQ.
4. Feature toggled off/on at runtime (Settings.Enabled) and savestate load with and without the "NELO" section; Reset while the outgoing voice is fading.
5. Driver snapshot not recognised (ChanOwnerValid false): the ALLOCATABLE_CHANNEL fallback when BGM and SFX channel masks overlap (HeartGold: BGM 0xA7FE, SE 0xD800).
6. Threading: Render() on the audio thread vs OnPxiWord/OnFrame/EnterHostMode on the emu thread; what state is read without the renderer mutex (Settings, HostP, HostMutedPlayer in SPU::Mix on the emu thread is fine; check BgmRenderer internals, the outgoing-voice swap, Load during Render, and the Android readAudioOutput path).
7.
